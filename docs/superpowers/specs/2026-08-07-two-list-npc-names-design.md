# Two NPC name lists, and a matcher that cannot explode

Date: 2026-08-07
Branch: `design/two-list-npc-names` (not merged; main is being tested separately)

## The problem

`NpcNameMatcher` builds **one compiled alternation regex per category** from every name it is given:

```csharp
var pattern = $@"(?<![\p{{L}}\p{{N}}])(?:{string.Join("|", normalized)})(?![\p{{L}}\p{{N}}])";
return new Regex(pattern, RegexOptions.IgnoreCase | RegexOptions.Compiled);
```

"Refresh NPC list from wiki" merges additively into `npc-name-list.json`, so that file only grows. A
full scrape produces **21,340 entries, 20,115 distinct**. At that size:

- Three reporters, and the maintainer, have had the game close instantly to desktop while scanning or
  building the Search index. Both paths call `Prepare()`, which builds the matcher before touching a
  single mod. A crash log ends at `[Scan:1] worker started` with nothing after.
- "Reset plugin data and reload" fixes it. That deletes `npc-name-list.json`.
- Classification degrades badly. 20,115 names, 5,775 of them a single token, match almost any mod
  title. Gear mods were being filed as NPC, which is why "By Mod Type Detailed" silently stopped
  splitting gear by slot.

0.5.3.1 already ships a stopgap: an oversized list is backed up, replaced with the bundled seed, and
the refresh button is disabled. This spec is the actual fix.

### What is NOT established

**The crash mechanism is unknown.** This matters enough to state before any design follows from it.

Measured against the real 20,115-name list, outside the game:

| | Result |
|---|---|
| Regex construction | ~240ms for all three categories |
| First match (JIT of the compiled pattern) | ~2.6s NPCs, ~1.3s enemies, 63ms bosses |
| Subsequent matches | 5–46ms, scaling linearly with mod-name length |
| Memory | ~71MB working set, ~21MB managed heap |

Slow and wasteful, but survivable. No stack overflow, no OOM, no crash. Two earlier hypotheses,
oversized-alternation stack overflow and catastrophic backtracking, were tested and **disproved**.

So the correlation between the large list and the crash is strong and reproducible, and the
explanation is not. Everything below is justified on correctness and classification quality, which
stand on their own evidence. **Nothing here may be presented as a proven crash fix.**

## Design

### Two lists

| List | Location | Origin | Default |
|---|---|---|---|
| **Static** | embedded resource in the plugin | hand-curated | always on |
| **Scraped** | `npc-name-list-scraped.json` in the config directory | wiki refresh | off |

The static list is **827 names**: 133 story characters and distinctive surnames, 15 enemies, 679
bosses and primals. It is 4.1% of the wiki scrape and is the list the plugin classifies against out
of the box. It ships as an embedded resource, like today's seed, so it cannot be corrupted or grown
by anything at runtime.

The scraped list is what the wiki refresh produces. It is **additional**, never a replacement: the
matcher is built from static ∪ scraped. A user who never opts in is unaffected by anything the wiki
does.

#### Why a curated static list rather than a filtered scrape

Filtering cannot produce this list. Measured on the real data:

- Canonicalizing wiki disambiguation (`(Limsa Lominsa)`, `/Purchase ...`) removes only **7.2%**, and
  slightly *raises* the proportion of single-token entries, which are the dangerous ones.
- Frequency cannot separate character names from role nouns. `Salvager` appears 3 times, `Galvus` 5,
  `Tia` 21, `Handler` 13. No threshold keeps Zenos and drops Calamity Salvager.
- The wiki has no fame signal. `Y'shtola` and `T'ohsoq` are indistinguishable in the data. "Names
  people make mods of" is human judgement and has to be curated.

The static list was generated by tiering the scrape (Garlean particles, boss-category membership,
multi-category membership, apostrophes, rare last tokens) and then hand-edited. The generator is a
one-off; the list is now the artifact and is maintained by hand and by community review.

#### Refresh becomes replace, not merge

`MergeAdditive` is the reason the file grew without bound. The refresh writes a **snapshot**:

```
scraped file = this run's wiki results, minus exclusions
```

Re-running a refresh cannot make the file larger than the wiki. The static list is never touched by
a refresh, so a bad scrape cannot damage the default behaviour.

`Excluded` keeps its current meaning and continues to be honoured.

#### Opt-in, and what gates it

The Sort tab gets a checkbox: **"Also use the NPC list scraped from the wiki"**, default off, with a
line explaining that it adds roughly 20,000 names, improves coverage of minor NPCs, and makes false
matches more likely.

**The checkbox stays disabled, and the refresh button with it, until the crash is reproduced and the
new matcher is verified against a full 20,115-name list in-game.** Shipping the toggle enabled on the
strength of "the new structure looks safer" would re-arm a failure whose cause we cannot name. The
size guard from 0.5.3.1 stays in place underneath as a backstop.

That verification is a release gate, not a task in this spec.

### The matcher

Replace the three compiled regexes with a first-token index.

Measured on the real 20,115 names:

| | |
|---|---|
| Distinct first tokens | 9,886 |
| Median candidates per bucket | **1** |
| p99 | 18 |
| Max (`territorial`) | 185 |
| Tokens per name | mean 2.19, p99 11, max 15 |

So matching goes from "test against 20,115 alternatives" to "one dictionary lookup, then a median of
one comparison".

```csharp
[Flags]
enum NpcNameKinds { None = 0, Npc = 1, Enemy = 2, Boss = 4 }

sealed record NpcNameEntry(string[] Tokens, NpcNameKinds Kinds);

// first token (normalized) -> entries starting with it, in the ordering defined below
Dictionary<string, NpcNameEntry[]>
```

Matching a mod name: normalize, tokenize once, then for each token position look up the bucket and
compare candidates in order, returning the first whole-token match.

#### Bucket ordering is defined, not implied

"Longest first" is ambiguous, and the answer has to be deterministic across runtimes. Entries within
a bucket are sorted by:

1. **Descending token count** — a match consumes tokens, so the longest match is the one consuming
   most of them. `Alka Zolka the Slayer` must be tried before `Alka Zolka`.
2. **Descending normalized character length** — tie-break for equal token counts.
3. **Ordinal comparison of the normalized name** — a total order, so the result never depends on the
   input file's order or on sort stability.

With this ordering, "the first match found is the longest match" is a property of the sort rather
than an accident, and cases like `Foo-Bar` / `Foo Bar` / `Foo Bax` resolve identically every run.

#### Category membership is merged, not duplicated

848 of 857 bosses also appear in Enemies and 372 names appear in both NPCs and Enemies, so the same
normalized name would otherwise occupy several slots in one bucket and precedence would fall out of
sort order by accident.

Instead, construction merges them:

```
Bahamut -> Boss | Enemy
```

One entry, one comparison. `Match` then resolves the flags through the existing precedence rule
(NPC, then Boss, then Enemy) and returns a single `NpcNameKind`, so `SubCategoryFor` and every
caller downstream are unchanged. Precedence becomes structural rather than incidental.

#### Tokenization is Unicode, not ASCII

Tokens are maximal runs where `Rune.IsLetterOrDigit` is true, iterating by `Rune` rather than by
`char`. This matters: `char.IsLetterOrDigit` works on UTF-16 code units and mishandles anything
outside the BMP, and mod titles in this community routinely contain emoji and decorative symbols.
The name list itself already contains non-Latin entries such as `ベア`.

This is a third deliberate behaviour change, alongside the separator loosening below: today's regex
`\p{L}\p{N}` classes are also applied per UTF-16 unit, so a non-BMP character currently splits
inconsistently. Rune-based tokenization fixes that, and it is listed here so the difference is
recorded rather than found later.

**A trie is not warranted.** It was considered and rejected on the data: at mean 2.19 tokens and a
median bucket of one, there is no prefix depth for it to exploit. The dictionary gets the entire
asymptotic win for a fraction of the code. If the list ever grows an order of magnitude and buckets
get deep, revisit.

#### Semantics that must not change

These are current behaviour and each needs a test that fails if it is lost:

- **Case-insensitive.**
- **Boundaries are "not adjacent to a Unicode letter or digit"**, deliberately not `\b`. `_Zenos_`
  matches on purpose; the existing comment says so. Tokenizing on non-letter/non-digit preserves
  this, but underscore must not be treated as a word character.
- **Longest match wins**, so a mod matching both `Alka Zolka` and `Alka Zolka the Slayer` reports the
  longer.
- **Normalization is NFC plus curly-to-straight apostrophe folding.** Both the stored names and the
  mod name go through the same function.
- **Category precedence stays NPC, then Boss, then Enemy**, as `Match` does today.

Two behaviours **do** change deliberately. The first is Rune-based tokenization, described above.

The second is a loosening around separators. Today `Y'shtola` is a single regex
alternative matching that exact text. Under token matching, `Y'shtola` tokenizes to `y` + `shtola`,
so `Y-shtola` and `Y shtola` would also match. This is an improvement for real mod titles, which use
inconsistent punctuation, and it must be stated rather than discovered. The list carries both
`Y'shtola` and `Yshtola` today precisely because of this problem; after the change the second entry
becomes redundant but is harmless.

#### Pruning entries that cannot matter

`ModTypeClassifier.Classify` uses `nameMatch.Kind` and **discards `nameMatch.Name`**. So an entry that
only matches when a shorter entry also matches can never change an outcome. On the static list that
was 61 entries (`Alisaie Leveilleur`, `Zenos yae Galvus`, `Y'shtola Rhul`, ...), already removed.

**This is only safe while the matched name is unused.** If a future feature surfaces which character
matched (a "sort by character" folder, say), full names stop being redundant. The static list carries
a comment saying so, and this spec is the record.

Distinctive surnames are kept as standalone entries instead: `Galvus` covers Zenos, Varis and Solus
in one entry, and `Leveilleur` catches a mod titled "Leveilleur Twins" that no given name would.
`Waters`, `Tia`, `Taru`, `Warde` and `Feare` are excluded as ordinary words or too short.

### Migration

Existing installs have `npc-name-list.json`, possibly 20,000 names, possibly already replaced by
0.5.3.1's guard.

On first run of the new version, by case, and **nothing is ever overwritten or deleted**:

| Legacy `npc-name-list.json` | `npc-name-list-scraped.json` | Action |
|---|---|---|
| exists | absent | rename legacy to scraped |
| exists | exists | **leave both untouched**, prefer scraped, log a warning naming the un-migrated legacy file |
| absent | exists | no-op |
| absent | absent | no-op; the static list is embedded |

Both files existing is reachable through a partial or interrupted migration, a downgrade-then-upgrade
cycle, or a user copying files by hand. Overwriting either would destroy data in exactly the
situation where the user is least likely to have a copy. Cleanup of a stranded legacy file is left as
a later decision rather than done silently here.

`npc-name-list.json` is never written again.

The 0.5.3.1 oversize guard applies to the scraped list when opted in, unchanged.

## Short names are kept

`Yda`, `Amon`, `Krile`, `Lyse`, `Ryne`, `Sadu`, `Seto`, `Venat`, `Zenos`, `Titan`, `Phoenix`,
`Shiva` and similar stay in the static list. They are real characters and primals that people
genuinely make mods of.

The cost is accepted knowingly: they will match unrelated mods whose titles contain those words as
whole tokens. At 827 curated names this is a much smaller problem than at 20,115, but it is not zero,
and it is the most likely source of remaining misclassification.

A match-strength model — multi-token names strong, short single tokens requiring corroborating
evidence before overriding gear-slot data — is the principled fix. It is **explicitly out of scope
here**, because it changes how every user's library sorts and must not ride inside a change already
touching classification. It gets its own spec.

## Testing

**Matcher equivalence.** The strongest available guard against a semantic regression: build the old
regex matcher and the new index matcher from the same list and run both over a corpus of mod names.

Global equality is **not** the assertion, because this change deliberately loosens two things. The
test uses two corpora with different rules:

| Corpus | Assertion |
|---|---|
| **Legacy-equivalence** — the static list's names in realistic mod titles, plus decorative non-matching titles, all with conventional punctuation | old and new must agree exactly |
| **Intentional-difference** — separator variants (`Y-shtola`, `Y shtola`) and non-BMP characters adjacent to names | old and new must differ, in exactly the documented way |

Splitting it this way stops a future test author from either weakening the equality assertion until
it passes, or being unable to tell a real regression from the two known differences. Both corpora are
temporary and are deleted along with the old matcher.

**Allocation behaviour.** Removing the regex is not automatically a win if matching allocates
heavily: a scan calls `Match` once per mod, so a normalize-plus-split-plus-token-array per call is
2,242 allocations' worth of transient garbage on a large library, on the background thread. The
target is "allocate while indexing, allocate little while matching". A zero-allocation implementation
is not required for this change, but per-match allocation is measured and recorded rather than
assumed, so a later regression has a baseline to fail against.

**Semantics** (one test each, all listed above): case-insensitivity, `_Zenos_` matching, longest-match
preference, apostrophe and NFC folding, NPC-over-Boss-over-Enemy precedence, and the newly-loosened
separator behaviour asserted explicitly rather than left implicit.

**Scale.** Building the matcher from 25,000 names and matching several thousand mod names completes
within a generous time budget, with no `Regex` anywhere in `NpcNameMatcher` — enforced by an
architecture test, so the giant alternation cannot come back by accident.

**Lists.** Static list loads from the embedded resource; a missing or corrupt scraped file degrades
to static-only with a warning and never throws; opt-out ignores the scraped file entirely; opt-in
unions the two; a refresh replaces the scraped file rather than growing it; `Excluded` is honoured.

**Migration.** An existing `npc-name-list.json` is renamed on first run; a run with none present is a
no-op; the renamed file is not consulted while the toggle is off.

## Sequencing

1. **Matcher rewrite**, static list only, toggle absent. Ships as the default experience.
2. **Migration and the scraped-list plumbing**, toggle present but disabled.
3. **Reproduce the crash** with the old matcher and a full list, then verify the new matcher against
   the same list in-game. Only this justifies enabling the toggle.
4. **Match-strength model**, separately specced.

Steps 1 and 2 are safe to ship without step 3, because with the toggle off nobody loads a large list.
